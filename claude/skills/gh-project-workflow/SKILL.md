# GH Project Workflow

Four `kit` commands run the GitHub side of the flow (#95; in dev-kit itself, `bb bin/kit …`). The board, repository and base branch come
from the `GHWF_*` variables in `.claude/settings.json` (generated by dev-kit from `kit.edn`):

| Variable | Meaning |
|---|---|
| `GHWF_OWNER` | board owner (user login) |
| `GHWF_PROJECT_NUMBER` | board number |
| `GHWF_REPO` | `owner/repo` of this project, used when the folder has no GitHub origin: the folder's origin comes first, so a worktree of another repository acts on that repository (#81) |
| `GHWF_DEFAULT_BASE` | base branch, `main` |
| `GHWF_SHOWCASE` | the board's Showcase option for this project |

Board fields: Status (Backlog / Ready / In progress / In review / Done), Priority
(Urgent / High / Medium / Low), Size (XS–XL), Showcase, Iteration, Start date, Due date.
All are board fields, set by name.

## Start: issue + board + branch

```bash
.shared/bin/kit start \
  --title "Add landing page" \
  --body-file /path/to/body.md \
  --priority High \
  --size S \
  --status "In progress"
```

- `--priority` is required; `kit start` refuses to file an issue without one.
- Reuses open work with the same title in this repository instead of filing a duplicate: an
  open issue, or a board card not in Done; a same-title draft card is converted into the issue.
  `--issue <n>` names the work outright: no title is matched, and #n is put on the board (#12).
- A board update that fails stops `kit start`, `kit finish` and `kit merge` alike, with GitHub's
  reason, its likely cause and the fix (#41). One field alone is set with
  `.shared/bin/kit board set <board> <owner> <issue-url> <field> <option>`.
- Creates the branch with `gh issue develop` and checks it out (`<number>-<slug>`);
  `--no-checkout` creates it without touching the working tree, `--skip-branch` creates none.
- Prints `Issue Number`, `Issue URL` and the branch.

## Finish, step 1: commit, push, PR, In review

From the issue branch:

```bash
.shared/bin/kit finish \
  --type feat \
  --add path/one --add path/two \
  --commit-message-file /path/to/message.txt \
  --pr-body-file /path/to/pr.md
```

- Subject: `--summary`, else the first line of `--commit-message-file`, else the issue title
  with its first letter lowered; it must read `type(GH-<issue>): summary`. The PR title is the
  same subject; squash merge makes it the commit on `main`.
- Every input is checked before the commit and the push (body file, `ADR:` line, subject).
- Only an open pull request counts as the branch's PR.
- The PR body must contain an `ADR:` line (`ADR: none` or `ADR: adr/NNNN-....md`) and states
  what was verified and what was not. `Closes #<issue>` is added when missing.
- `--no-commit` pushes and opens the PR for commits already on the branch.
- Requests a review from the code owners (`GHWF_REVIEWERS`, from `:owners`; not on a draft, which
  asks nobody) and assigns the PR to
  the person behind the agent (`GHWF_HUMAN`, their own gh login, written by `kit init`).
- Never merges itself. Auto-merge (squash) is how the owner's Approve of the latest commit merges.
  The card moves to **In review**. If the repository does not allow auto-merge, it warns and
  names the setting.
- It asks `main` for `.github/workflows/ready-when-green.yml` (ADR-0007). With it, the PR opens
  as a **draft**, with no auto-merge: the workflow marks it ready, which asks the owners for a
  review, and turns auto-merge on, once every required check passed. Without it, the PR opens
  ready, with auto-merge on. If `main` cannot be read, it stops before the commit.
- `--hold` opens the PR with the label `hold` (made when missing), or adds it to the open PR: the
  workflow leaves such a draft alone. It needs the workflow on `main`; where it is missing, it
  stops before the commit and says to run without `--hold`.
- Then watch the checks in the background, as the failure alarm (`run_in_background`):
  `gh pr checks <pr> --watch --fail-fast --required`. Ask the owner for the Approve once the PR
  is ready (a held PR is not ready until `kit release`). A watch started right after a push can
  end before the head's checks exist: `kit checks` (#109) closes that gap.

## Release a held PR

```bash
.shared/bin/kit release            # from the held PR's branch; or --pr <number>
```

When the PR it waited for has merged: removes `hold`, marks the PR ready, turns on auto-merge. It
also frees a draft that was never held but that nothing marked ready (a required check from
outside the CI workflow, CI renamed or disabled), once its checks have passed.
While a required check on the head is not green it changes nothing and names the check; run it
again when that check has passed.

## Merge after approval

The owner's Approve of the latest commit is the word; no chat message is needed. Usually
auto-merge has merged the PR by the time the agent looks. Either way, run:

```bash
.shared/bin/kit merge
```

Run it as a background command; the guard refuses it otherwise (#109). It looks at the PR every 10 seconds inside, and the agent is
woken when it exits. Never wait for it, or for checks, with `sleep` or `--watch` in the foreground.

- Open PR: refuses without the owner's Approve and says so. A branch behind `main` is updated
  first by merging `main` into it, which keeps the approval (tested on #45). Then it turns on
  auto-merge and waits until GitHub merges. It stops, and names the reason, when merging became
  impossible: the PR was closed, a required check failed (each named with its link), the branch
  conflicts (`DIRTY`), or the approval is gone. No time limit ends it.
- PR already merged by auto-merge: only the closeout.
- Closeout after a confirmed `MERGED`: card **Done**, branch deleted locally and on GitHub,
  back to `main` (or detached on `origin/main` when `main` is checked out in another worktree).
  A PR that did not merge keeps its branch.

It runs without a permission prompt: the server enforces the approval, and the `main` ruleset
merges only an up-to-date branch with every review thread resolved. A raw `gh pr merge` stays
under `ask`.

## Waiting for checks

```bash
.shared/bin/kit checks [--pr <number>]
```

Run it as a background command too (the guard refuses it otherwise). No time limit ends it. It
reads the checks the base branch requires from its rulesets (classic branch protection needs
admin), then waits until each exists on the head commit (right after a push they are not
registered yet) and has finished.

| Exit | Meaning |
|---|---|
| 0 | all passed, or the base requires none |
| 1 | a required check failed or was cancelled: each is named with its link, at once, without waiting for the others |
| 2 | no result: the PR closed or merged, its head moved (run it again for the new head), or gh could not be read (its message is printed) |

`kit merge` ends the same way on its own reasons: PR closed, a required check failed, a
conflict (`DIRTY`), the approval gone; it names which and says what to do.
